## 二、流程

### 2.1 本地开发：两个服务都要起

```bash
# 终端 1 —— 后端
cd workers/chat && npx wrangler dev --port 8787

# 终端 2 —— 前端。两个参数**一个都不能少**
HUGO_PARAMS_CHAT_APIBASE=http://localhost:8787 \
HUGO_PARAMS_CHAT_MEDIABASE=http://localhost:8787/api/media \
hugo server --port 1313 --bind 127.0.0.1 --disableFastRender --renderToMemory
```

三条硬要求：

1. **浏览器访问必须用 `http://localhost:1313`，不能是 `127.0.0.1:1313`。**
   Cookie 的 SameSite 只比 scheme + 域名、**不比端口**，换成 IP 就变跨站，
   Lax Cookie 一律不带 → 症状是「登录接口 200，紧接着 `/api/me` 401」。
2. **`HUGO_PARAMS_CHAT_APIBASE` 漏了会打线上 API**，`MEDIABASE` 漏了图不渲染。
   `chat.js` 里有一道防呆（本地页面 + API 指向远端 → 当场红字报错），但别指望它兜。
3. **`--renderToMemory` 不写 `public/`，所以 `frontend-test` 的夹具不会自动更新。**
   改了短代码之后必须另外跑一次 `hugo --minify`。

### 2.2 改完代码该跑什么

| 改了什么 | 至少跑这些 |
|---|---|
| 只改 CSS / 短代码 | `hugo --minify` → `verify-build` → `frontend-test` |
| 只改后端路由 / 模型 | `typecheck` → `smoke` |
| **改限流阈值或调用点** | `rate-limit-test`（唯一能看见真实阈值的一档） |
| 改配额 / 清空房间 / 上传 | `purge-test` + `smoke` |
| 改迁移 | `npm run migrate:local` → `smoke` |
| 要推送了 | 六个全跑一遍 |

`deploy` job：仅 push，`needs: build`，就一步 `Deploy to GitHub Pages`。

**三个必须知道的事实：**

- **CI 里没有 `smoke` / `frontend-test` / `purge-test` / `rate-limit-test`** ——
  它们要 `wrangler dev`，起服务成本太高。所以「CI 全绿」**不等于**后端行为正确，
  推之前必须本地全跑。
- **`Checkout` 红掉会跳过后面所有步骤**（等于一次测试都没跑）。它拉的是 `.gitmodules`
  里 gitee 的 PaperMod fork，偶发超时。看到站点没更新，**先看是哪一步红的**，
  别先怀疑自己的改动；重试手法是空提交再推。
- **PR 不部署、也不拉 wiki**（fork 拿不到 secret）。PR 构建验的是三件事：
  Hugo 能不能构建、聊天室脚本归属对不对、后端类型过不过。

### 2.4 部署

**前端**：`push main` 即自动，CI 完成即上线。

**后端**：手动，**顺序不能反**：

```bash
cd workers/chat
npm run migrate:remote   # 1) 先把库改好
npm run deploy           # 2) 再部署 Worker
```

反过来的后果：Worker 已经在读写一个还不存在的列 → 所有发消息都失败。
`migrate:remote` 是幂等的，没有待应用迁移时输出 `No migrations to apply!`。

### 2.5 上线后验证（只读）

```bash
cd workers/chat && npm run probe-production
```

它依次打 `/api/health`、CORS 预检、非法注册（400）、不存在账号登录（401）、
`/chat/` 页面骨架和 `chat.js` 引用 —— **不会写入任何数据**。

注意：它验的是「服务活着、接线对」，**验不了阈值**（要验就得往生产打满额度）。

### 2.6 已知测试盲区

写出来是为了避免以后误以为覆盖了。两条分支**在当前框架里构造不出来**：

1. **`evictIfExpired()` 真正关掉连接那一下。** 要触发得让连接上的 `exp` 在测试中途过去，
   而它来自 access token（测试里有效期 30 分钟）。手工签短 exp 的 JWT 等于在测试里
   重实现一遍签名 —— 库改了 claim 约定，测试会因为错误的原因变红，比没有更误导。
   现在只有 3 条静态断言守着。**静态断言拦得住「调用被删掉」，拦不住「函数体写错了」。**
2. **`markUpload()` 返回 `false` 那个分支**（额度在预检之后被抢走）。预检和守卫用同一组
   条件，单线程下永远一致，要分歧必须有真并发 —— 而并发的上传会先撞上上传限流
   （10 秒 10 次），两个 429 混在一起分不清是谁挡的。**拒绝路径**目前只由 `smoke`
   从外侧验（塞满账本 → 429 → 清空 → 又能传）。

### 3.5 `rate-limit-test`（22 项 / 7 组）

**唯一能验出「阈值到底放行多少次」的一档。** 它自己起一个 `STRICT_RATE_LIMIT=true`
的 dev server（8789），所以绕开了本地放宽。
其余套件跑在放宽模式，429 断言在那边**永远绿**，等于没测。

**① 准备：确认限流在本进程里真的生效**

- 限流处于生效状态（否则本脚本的断言都不成立）

**② 注册限流**

- 放行 4 次（第 5 次记账时就 hits=5，被拦下）
- 第 5 次起被限流 429

**③ 登录限流**

- 前置：账号建出来了
- 密码正确时登录成功（限流只记失败）
- 前 10 次是 401（凭据错误）
- 第 11 次起返回 429

**④ 撤回限流**

- 前 30 次走到业务逻辑（404）
- 第 31 次起返回 429
- 429 之后不会偶尔再放行一次
- 429 带 Retry-After
- 限流是按账号算的，换个人不受影响

**⑤ 发言限流**

- 前 10 条都发得出去（201）
- 第 11 条起被限流 429
- 429 带 Retry-After

**⑥ refresh 限流**

- 前 30 次 refresh 成功
- 第 31 次起返回 429
- 废 token 先正常返回 401，不是上来就挡
- 废 token 打满后也被 429 限住（不是绕过限流的后门）

**⑦ 上传限流**

- 前 10 个文件传得上去（201）
- 第 11 个起被限流 429
- 429 带 Retry-After

> **新增一条限流就在这里顺手加一节。** 断言方向固定是
> 「前 N 次必须成功、第 N+1 次才 429」—— 因为 `consumeRateLimit` 是「先记账再判断」，
> 常量写的是 `ALLOWED + 1`，只看常量文件很容易算错。
> （注册那条反过来：常量 `5` 没有 `+1`，所以只放行 4 次，这是有意保留的已知 off-by-one。）

### 建议**留着**的「高维护税」断言

`㉑ 确认窗口是 5 秒`、`㉑ 确认文字是「确认删除？」`、
